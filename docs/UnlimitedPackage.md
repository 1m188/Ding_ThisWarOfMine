# 无限背包空间 (UnlimitedPackage)

## 功能语义

背包容量决定角色能携带多少物品。原版游戏中每个角色初始只有少量格子（基础 10 格左右），需要靠背包装备（如双肩包 +10 格）扩容。物品按宽度占格：堆叠的同类物品每件占 1 格宽，例如 5 发子弹堆叠后占 1~2 格。

无限背包空间让所有容量判定恒为大值，任何物品都能放入。实现上有两类语义：一类是冻结当前容量值不减少；另一类是把容量上限直接改成大数（如 300 格）。FLiNG 属于后者。

## 游戏实现

游戏用"容器对象"表示一个背包。核心布局：

- 容器对象 `+0x70`：int 类型容量（capacity），即总格数；装备带来的扩容（如双肩包 +10 格）就是直接加到这个字段上。
- 容器对象 `+0xBC`：int 类型「额外空闲格」。它不参与 `+0x70` 的容量本身，只在面向界面的空闲格查询（RVA 0x4853F0）里被加到空闲格数上，所以它影响界面显示，不影响放入判定。
- 容器对象 `+0x18`：条目数组计数；`+0x20`：条目数组指针，每个条目 0x40 字节。
- 条目内 `+0x28`：int 堆叠数量；`+0x18`：物品定义指针，其 `+0x44` 为每件占格宽。

容量计算的核心函数（记为 CountFreeSlots，RVA 0x3DF360）：遍历条目数组，每个条目占用 `ceil(数量/格宽)` 格，返回 `capacity − 总占用`。所有"还能不能放"的判断都走它：物品放入、拾取判断、容量溢出回收。

界面侧的查询（RVA 0x4853F0）返回 `CountFreeSlots() + 容器对象 +0xBC`，也就是"这个背包还能放多少格"，供 UI 显示使用；容器或容器内条目指针为空时它返回 -1。UI 面板初始化大函数（RVA 0x485EA0 起）在构建界面时会读一次容器容量写入 UI 配置对象 `+0x44`，读的指令是 `mov ecx,[rdx+0x70]`（RVA 0x485F24）。

容量 `+0x70` 只有三种时候会变，**没有每帧重算**：

- 打开背包界面时，用角色模板上的 `InventorySlots` 重新算一遍容量写进 `+0x70`。取值函数是 RVA 0x2CDD00，整个函数只有三条指令：`mov rax,[rcx+0x28]`（角色身上的模板对象）、`mov eax,[rax+0x1a0]`（模板的 `InventorySlots`）、`ret`。写入发生在背包界面初始化函数 RVA 0x406BE0 里：`*(int *)(容器 + 0x70) = 取值()`。所以每次打开背包，容量都会被刷新成模板里的数字——这也是风灵月影把钩子挂在这个时机的原因。
- 穿脱装备时增量加减。放入物品走 RVA 0x2CCD40：找到物品定义后取它 `+0x2DC` 处的容量加成，非零就调用 RVA 0x3DEA10 加容量；卸下物品走 RVA 0x2D88C0：同一个字段，调用 RVA 0x3DEA10 减回去。
- 容器在别处建立时也会给一个初值（同源的模板数据），因此只改容器字段的话，下次打开界面就被覆盖回原值。

物品模板上还有一个 `InventorySlots` 属性（物品模板偏移 `+0x1A0`，int 型），在模板属性注册函数 RVA 0x2D2980 里注册，含义是"这件物品作为容器时有多少格"。容器类物品（背包、箱子）和角色的基础携带格数都来自这里，而不是代码里的常数。

容量设置函数（RVA 0x3DEA10，SetCapacity）：正数直接加到 `+0x70` 基础容量上；负数时先算当前空闲格，空格不够就从条目数组尾部往前逐个压缩堆叠、回收物品（走 RVA 0x3DFD50），最后再把 `+0x70` 加上这个负数。即游戏原生的"穿背包装备扩容"就是改 `+0x70`。

## 可选的功能实现方法

**本项目当前实现**：改容量取值函数，补丁在 RVA `0x2CDD00`（原始 11 字节换成 `mov eax,300; ret` + 5 个空操作）。

**改容量取值函数（首选，纯代码改写，不用代码页）**：把 RVA 0x2CDD00 处的 11 条字节 `48 8B 41 28 8B 80 A0 01 00 00 C3` 改成 `B8 2C 01 00 00 C3 90 90 90 90 90`（`mov eax,300; ret` + 5 个空操作）。这个函数只做"读出模板里的格数"这一件事，改完之后所有走它的地方拿到的都是 300：打开背包界面时刷新的容量、界面格子数、以及另外两个调用点。显示和判定一致，也不需要申请可执行页。

**直接写容器容量（简单，纯数据）**：拿到容器对象地址后把 `+0x70` 写成大数（如 300）。缺点有两个：下次打开背包界面时会被模板里的 `InventorySlots` 覆盖回去；之后再穿脱带容量的装备，游戏会在这个值上加减。适合先验证数据通路，不适合做长期生效的功能。

**改空闲格函数（纯代码改写，不用代码页）**：把 RVA 0x3DF360 的开头 6 字节改成 `B8 2C 01 00 00 C3`（`mov eax,300; ret`）。所有"还能不能放"的判断都恒为 300 格。局限是界面里显示的容量数字仍来自 `+0x70`，如果 UI 按容量数字生成格子，界面上的格数不会跟着变；只在不想动容量取值函数时才用。

**改物品定义的容量加成**：物品定义 `+0x2DC` 处的容量加成改成大数，穿上一件带容量的装备（背包）就直接扩容。依赖"身上有一件带容量的装备"这个前提。

**钩容量读取点（FLiNG 方案）**：在 UI 面板重建读容量的位置植入跳转，每次重建时把 `+0x70` 强写为大数，显示与判定都一致；代价是要申请可执行页。与无限生命的"驻留钩子+旗标"不同，这个钩子可以是无状态的——装上即生效，拆掉即恢复，无需旗标分流。

**改数据包（Mod 路线）**：通过官方 ModTools 修改物品定义的占格宽或装备的容量加成，不是修改器但能达成类似效果。

## FLiNG 实现

FLiNG Num2 的钩子挂在 UI 面板初始化函数内部（RVA 0x485F24），钩住两条指令：`mov ecx,[rdx+0x70]`（读容器容量）和 `mov [rax+0x44],ecx`（写入 UI 配置）。植入的桩代码只有一句话：

```asm
mov dword ptr [rdx+0x70], 300   ; 把容器容量强写为 300 格
; 然后原样执行被替换的两条指令，回到原流程
```

即每次 UI 初始化读容量之前，先把容量改成 300。由于容量计算函数读的是同一个 `+0x70` 字段，所有容量判定都看到 300 格。

这两条被替换的指令各 3 字节，原位一共只有 6 字节，放不下"写容量 + 回填界面字段"这一串指令，所以它必须跳到自己申请的代码页去执行，执行完再跳回来。

与无限生命功能的重要差异：无限生命的桩有旗标分流（远页 `+0x200` 处 0/1 切换，钩子常驻），而这个功能的桩无旗标——开启时装钩子，关闭时直接把 `.text` 还原成原始字节。它是对"读容量"指令的定点改写，不依赖任何状态位。副作用是关闭功能时如果 UI 没有重新初始化，`+0x70` 里残留的 300 会保留到下次游戏重算容量（穿脱装备、重载存档）为止。

跳板结构与无限生命相同：`.text` 五字节跳转 → 游戏进程内预留近页（模块基址减 0x10000000）→ `FF 25` 绝对跳转 → 堆上新分配的远页桩代码 → 执行完毕跳回原指令后续。

它选"界面读容量"这一点而不是"容量取值函数"（RVA 0x2CDD00），是因为它整套功能都用同一套挂钩框架，复用现成的跳板与桩结构最省事；只追求效果的话，把取值函数改成常数更省——不用代码页，一行六字节即可。
