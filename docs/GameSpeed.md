# 游戏倍速 (GameSpeed)

## 功能语义

游戏里所有「时间」——人物走路、动作动画、挖土/撬锁/搜索的读条、制作和升级的进度、右上角的昼夜时钟——都从同一个时间基准换算出来。「游戏倍速」就是把这个基准按倍数改掉：设成 2 倍，世界就跑得比正常快一倍；设成 0.5 倍就是慢动作。

它和几个容易混的功能不一样：

- **瞬间制作**只改制作与升级的进度累加，不碰其它动作。
- **锁定白天 / 锁定晚上**只让时钟停住，世界里的动作照常进行。
- **游戏倍速是全局的**：一旦开启，人物动作、动画、读条、昼夜时钟同时变快，这也是它省事的地方。

边界要说清楚：

- 不改伤害、资源、耐久等任何数值逻辑，只改变「一帧算多久」。
- 渲染帧率不变，所以世界跑得更快时视觉上会出现动作跳帧、动画不连贯，这是必然现象，不是坏了。
- 倍速越高越容易看出动作抽帧，8 倍以上会明显像「瞬移」。
- 昼夜时钟也会一起变快。不想让白天被快进走完时，可以同时开「锁定白天时间」。
- 倍速作用在游戏进程内部，不改变系统或其它程序。

用法建议：跑图、等天黑、刷资源时开高倍速；需要精细操作时切回 1 倍。

## 游戏实现

### 时间只有一个来源

引擎用 Windows 高精度计数器（`QueryPerformanceCounter`）换算每帧时长：

```
本帧秒数 = (本次计数器值 − 上次计数器值) / 频率
```

频率在启动时由 `QueryPerformanceFrequency` 取得（本机是 10000000），存放在 `.data` 里，8 字节 double，**RVA 0x823FB8**；文件里是 0，启动时填入。

全工程有 **131 处**代码读这个值做换算（形如 `差值 * (1.0 / 频率)` 或 `差值 / 频率`），所以它是唯一的时间基准——改它一处，所有按时间走的系统一起变。

### 每帧增量分成两档

换算出来的秒数会被分发成至少两档全局 float 增量：

| RVA | 含义 | 谁在用 |
| --- | --- | --- |
| `0x140838800` | 真实时间增量 | 人物动作、动画、走路、字幕计时、夜间流程里那几段节奏等待 |
| `0x140838820` | 游戏时间增量 | 昼夜时钟进度、制作与升级时长、夜晚时钟的累计秒数 |

两者的写入点在主循环的更外层（经间接调用调度），静态分析没有定位到具体那条写入指令；但实验证明两档都来自上面那个频率换算。

### 昼夜时钟怎么用这两档

- 白天进度：`进度 += 游戏时间增量 / 360`，360 是白天的阶段长度（存在时钟参数对象基址 `0x923EE0` 的 `+0x48`，RVA `0x923F28`）；进度超过 1.0 就进入「当天结束」流程。
- 夜晚进度：`夜晚累计 += 真实时间增量`，再除以夜晚阶段长度（RVA `0x925114`）得到 0~1 的进度。

### 实测验证

在运行中的游戏里把 RVA `0x823FB8` 从 `10000000` 依次改成 `5000000`（2 倍速）、`2500000`（4 倍速），观察结果：

- 2 倍速：能感觉到一点变化，但很轻微；
- 4 倍速：动画、人物动作、读条、昼夜时钟全部明显变快。

⇒ 这个地址就是全局时间基准，改一处即可整体调速。

## 可选的功能实现方法

### 方案一：改时间基准（推荐）

开启时读取 RVA `0x823FB8` 的 8 字节 double，写入 `原值 ÷ 倍速`；关闭时写回读到的原值。

- 纯数据写入，不改任何指令，不需要在游戏进程里申请可执行页。
- 原值来自 QPC 频率，可能随机器和启动变化，所以必须「先读、再算、写回原值」，不能写死 `10000000`。
- 读到的值不在合理范围（1000 ~ 10^10 之外）说明游戏还没初始化时间系统，应放弃这次操作。

### 方案二：倍速 + 昼夜不变（可选）

如果希望「动作变快、屏幕上的钟照常走」，在方案一基础上再补两处数据：

- 白天分母 RVA `0x923F28`（= 360）乘以倍速；
- 夜晚分母 RVA `0x925114`（= 360）乘以倍速。

昼夜进度因此变慢，抵消时间基准变化的部分，只有动作与动画变快。代价是这两个数值还被别的计算读取（制作时长换算、夜晚剩余时间判断），需要逐处确认，风险高于方案一。

### 方案三：改指令里的乘数（不推荐）

找某处 `时间增量 × 常量` 的乘法改成更大的常量。问题是时间增量被上百处代码分别使用，只改一处覆盖不了全部系统，结果会变成「只有某几个东西变快」，不如改基准。

### 实现时要注意

- 倍速值建议做成档位循环（例如 2 → 4 → 8 → 1），按一次换一档，省得每次重开。
- 关闭功能时写回原值；开着倍速直接关游戏也没关系，重启后游戏会重新填入正常频率。
- 只写 8 字节对齐的 double，写入前备份并校验原值范围。

## FLiNG 实现

风灵月影里这项叫「设置游戏速度」，快捷键是小键盘 7，默认 2.5 倍，重复按在几档之间循环。

它没有改时间基准，而是**往游戏进程里注入一个自己带的模块**，由那个模块去替换游戏的时间换算代码：

| 环节 | 做法 |
| --- | --- |
| 提权 | 启动时 `OpenProcessToken` → `LookupPrivilegeValueW("SeDebugPrivilege")` → `AdjustTokenPrivileges` |
| 注入 | 把随包的 `TrSpeedHack_x64.dll`（文件里的产品名是 `Trainer Speedhack Helper Library`）释放到 `%LOCALAPPDATA%\FLiNGTrainer\`，再注入到 `This War of Mine.exe`；游戏进程的模块列表里能看到它 |
| 模块要用的 API | 运行时按名字解析 `VirtualAlloc`、`VirtualProtect`、`FlushInstructionCache`、`SuspendThread`、`ResumeThread`、`GetThreadContext`、`SetThreadContext`，以及 `QueryPerformanceCounter`、`GetTickCount`、`timeGetTime` |

这套 API 组合反映的思路是：在目标进程里申请一块可执行内存，把游戏的时间换算代码改成跳到自己的代码、执行完再跳回去；挂起/恢复线程是为了改写代码的那一瞬间不被打断。所以它确实属于「需要代码页」的那条路，和本项目的纯数据写入不是一回事。

两者对比：

- 本项目只写 `.data` 里的 8 字节频率，不注入模块、不申请可执行页、不挂起线程；风灵的模块在游戏进程里常驻，只有开关时才改代码。
- 实测风灵运行期间，游戏的频率字段（RVA `0x823FB8`）仍然是 `10000000`，说明它的调速完全不经过这个字段。
- 两套可以同时开，效果相乘：风灵 2.5 倍 × 本项目 2 倍 = 实际 5 倍。
