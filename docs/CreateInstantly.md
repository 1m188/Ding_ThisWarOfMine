# 瞬间制作物品 (CreateInstantly)

## 功能语义

- 游戏里的制作是"占用时间"的工序。在灶台做饭、在工作台做过滤器、在炼金台熬药，选好配方后设备进入制作状态，进度条随时间推进，走完才出成品。
- 一件东西做多久由配方决定：配方里有一项"制作小时数"（元数据 `CraftTimeInHours`，未填写时默认 1 小时），界面按游戏内小时显示。
- 瞬间制作物品就是让这段等待消失：指令下达后进度条立刻满格，成品立刻出现。
- 实现上有两种语义取向：
    - 把"进度增长"改成一步到位——每次推进直接加上一整段时长；
    - 把"总时长"改成零——按游戏自己的规则（时长为零即视为完成）立刻完成。
- 边界说明：材料是否足够、配方是否解锁由另外的逻辑判断，这个功能跳过的只有时间。另外，凡是由同一套计时代码驱动的工序都会一起被加速，这是共性而不是缺陷。

## 游戏实现

- 制作逻辑挂在设备实体上，由组件类承担。`KosovoCraftingComponent`（制作）、`KosovoConstructionComponent`（建造）、`KosovoUpgradeComponent`（升级）以及公共基类 `KosovoCraftingBaseComponent`，四个虚表在同一个槽位（偏移 0x120）都指向同一份"进度更新"实现（本样本 RVA 0x3455A0）。也就是说制作、建造、升级的进度推进是同一段代码。
- 组件对象里与计时有关的字段：
    - `+0x48`：状态。0 空闲、3 制作中、4 完成后的收尾、7 收尾结束（派发完成事件）；
    - `+0x4c`：关联记录索引，指向全局表里 0x310 字节一条的记录，用于后续通知；
    - `+0x50`：制作进度比例（0～1，1 表示完成；空闲时写 −1）；
    - `+0x54`：已累计的进度（秒）；
    - `+0x58`：本次制作的总时长（秒）；
    - `+0x5c`：完成后收尾的进度比例；
    - `+0x60`：收尾已累计（秒）；`+0x64`：收尾总时长（秒）；
    - `+0x109`：完成通知标志；`+0x118`：本次批次件数；`+0x11c`：进入批次时的件数。
- 每帧驱动：外部每帧以"组件 + 帧上下文（`+8` 处是本帧经过的秒数）"调用虚表 0x130 槽位（RVA 0x345510）。它先看状态，只有"制作中"才推进，然后算出本帧可用的时间片：
    - 一般情况下是 `min(总时长 − 已累计, 本帧经过的秒数)`，即这一帧过了多少真实时间就推进多少；
    - 批次件数大于 1 时额外加上 `件数 × 总时长`，让一帧内可以连做几件。
    算完把时间片作为参数调用 0x120 槽位的更新函数。更新函数可能把状态改成 4，于是剩余的帧时间再交给 0x138 槽位（RVA 0x345780）处理收尾。
- 更新函数（RVA 0x3455A0，477 字节）的核心流程：

    ```c
    if (状态 != 3) return;
    for (;;) {
        if (不是第一轮) { if (时间片耗尽) return; if (状态 != 3) return; }
        float 总时长 = this->总时长;                  // +0x58
        if (总时长 <= 0) { this->进度比例 = 1.0f; goto 完成; }
        if (时间片 < 0) 时间片 = 0;
        this->已累计 += 时间片;                        // +0x54，本样本 RVA 0x345622
        this->进度比例 = min(已累计 / 总时长, 1.0f);    // +0x50
        时间片 = (已累计 >= 总时长) ? 已累计 - 总时长 : 0;   // 余量留给下一轮
        if (进度比例 < 1.0f) continue;
    完成:
        if (收尾总时长 <= 0) { 调虚表 0x128 槽位; continue; }
        this->状态 = 4;
        成品 = 虚函数[0xC0](this);                     // 产出物品
        派发事件(载荷 = 成品, 名字 = "OnDeviceCraftingBegin");
        if (this->完成通知标志) {
            发两条通知事件（编号 0x117 / 0x74，关联 +0x4c 的记录）;
            this->完成通知标志 = 0;
        }
    }
    ```

- 完成后的收尾（RVA 0x345780）：状态 4 时把剩余时间累加到 `+0x60`，算出收尾比例写 `+0x5c`，派发 `"OnDeviceCraftingProgressUpdate"`；走完后调 0x128 槽位。状态 7 时派发 `"OnCraftingComplete"`，进度比例写回 −1，状态归零。
- 时长从哪来：制作指令的下发路径是 指令分发函数（RVA 0x3441B3）→ 开始制作函数（RVA 0x3435D0）。后者做四件事：
    - 读配方的制作小时数，`× 3600 ÷ 时钟压缩倍率` 换算成现实秒数，写进 `+0x58`；
    - 倍率由时钟对象给出（RVA 0x26E500），算式是"当天剩余小时数 × 3600 ÷ 一个现实秒数的分母"，因此它随一天内的进度变化：同一个"1 小时"的配方，一天里不同时刻换算出的现实秒数并不相同；
    - 再乘角色的速度倍率；角色带 `Kid` 标签时改用儿童倍率；
    - 收尾时长同样换算出 `+0x64`；最后状态置"制作中"，派发 `"OnBeginCrafting"`。
- 状态机小结：下达指令 → 制作中（3）→ 完成收尾（4）→ 收尾结束（7）→ 空闲（0）。

## 可选的功能实现方法

- 中和"进度增长"（首选，最简单）：把 `addss xmm6,[rdi+0x54]` 改成 `addss xmm6,xmm1` 再加一个 NOP——整条指令 5 字节，实际只有 2 个字节变化。此刻 xmm1 里正好装着本次制作的总时长（上一条指令刚读过 `+0x58`），于是每推进一次就加上一整个时长，进度比例直接顶到 1，制作在一帧内完成。不注入代码，关闭时写回原字节。
- 让"总时长"变成零：更新函数本身就有"时长为零即视为完成"的分支，所以只要让开始制作函数写进 `+0x58` 的值是 0，效果与上一条等价，区别只是改动位置落在"开始制作"而不是"推进进度"。可用 `F3 0F 5E F0 F3 0F 11 73 58`（`divss xmm6,xmm0` + `movss [rbx+0x58],xmm6`）这串 8 字节定位，它在整个文件里唯一；只凭 `divss xmm6,xmm0` 找会撞上 40 多处。
- 只加速制作、不加速建造与升级：三类工序共用同一段代码，光改那两个字节做不到区分。需要在钩子里判断组件类型（读虚表指针，只有制作组件才加速），代价是要自己搭跳板和桩代码。
- 纯数据方案：不改代码，每帧遍历所有制作组件，把已累计进度 `+0x54` 写成总时长 `+0x58`。好处是完全不碰代码段；坏处是要先能枚举出组件实例，得摸清实体与组件容器的结构，实现量比改几个字节大得多。
- 不建议的路线：加速游戏时钟也能"看起来变快"，但饥饿、疲劳、伤病、日夜节奏全都跟着变，不属于这个功能的语义。
- 定位锚点：补丁点所在的"`addss xmm6,[rdi+0x54]` + `movss [rdi+0x54],xmm6`"八字节序列在整个游戏文件里只有一处；更长的前导序列（比较 + 条件跳转 + 读时长 + 加 + 存回，22 字节）同样唯一。扫描定位时用后者更稳。

## FLiNG 实现

- 风灵月影对应样本 v6.0.0 Plus 8（2019 年 11 月）。它的 Num4 只改两个字节：RVA 0x345625 处的 `77 54` 变成 `F1 90`，整条指令由 `addss xmm6,[rdi+0x54]` 变成 `addss xmm6,xmm1` 加一个 NOP，正是上面第一条路线。
- 这是无状态功能：开启就是把这两个字节写进去，关闭就是把原字节写回来；没有跳板、没有远页代码、没有标志位。与它的无限生命（钩子 + 标志）风格完全不同。
- 为什么无限生命要用钩子、这个功能不用：无限生命要替换的是"值"（改成 9999999 或 0），两个字节改不出来，只能跳出去执行自己的代码；瞬间制作只需要换掉"加哪个数"，而正确的数正好已经在 xmm1 里，所以两个字节就够。
- 副作用：同一份实现服务于制作、建造、升级三类组件，所以这个开关同时让建造与家具升级瞬间完成。功能名只写了"制作物品"，实际覆盖面更大。
- 共存注意：它写入前不校验原始字节，直接覆盖。如果我们的实现也要改这两个字节，应先读一次确认当前内容，只在自己写过的前提下还原，避免把别人的补丁当成原字节覆盖掉。
