# 制作不消耗资源 (NoCost)

## 功能语义

游戏里做东西要扣材料：点下制作、建造或升级后，仓库里的木材、零件、材料按配方数量被扣掉，扣到零就整格消失。

「制作不消耗资源」就是让这一步不生效：材料照常参与判断、照常做出成品或盖出房子，但仓库里的数量一点不少。名字虽然叫「制作」，意图是**所有要花材料的操作都不扣**——制作、建造、家具升级一视同仁，可以随便花销。

还有一道更前面的门：材料数量不够时，游戏连「制作 / 建造 / 升级」的按钮都是灰的，点都点不了。这道门不止一处，打开工作台、选中配方、点下按钮，每一步都会重新判一次。所以本功能把这几处判定一起放开，材料为 0 也能选、能点、能开工，做完照样拿到成品或房子。

它和几个容易混的功能不一样：

- **无限资源**听起来像同一个东西，但游戏并没有「资源无限」的状态，实际能做到的就是「消耗时不扣」，所以功能名以「不消耗」为准。
- **无限背包空间**改的是「能放多少格」，不改数量。
- **无限工具耐久**改的是每件工具自己的耐久值，不改堆叠数量。
- **瞬间制作**改的是计时进度，不改材料。

覆盖面要说清楚：扣材料这一步是**一套公共逻辑**，制作、建造、家具升级都调它，所以一处改动三种操作同时生效。交易、丢弃、拾取、产出分发走的是另外的入口，不受影响。

## 游戏实现

### 物品放在哪

物品都在「容器」对象里，仓库、背包、工作台内部格用的是同一个结构：

| 偏移 | 类型 | 含义 |
| --- | --- | --- |
| `+0x18` | int | 条目数量 |
| `+0x20` | 指针 | 条目数组 |
| `+0x70` | int | 容量（格数） |

每个条目 0x40 字节：

| 偏移 | 含义 |
| --- | --- |
| `+0x18` | 物品定义指针（类别号取定义 `+0x180`） |
| `+0x20` | 物品定义指针（按它匹配「要取的是哪种」） |
| `+0x28` | 堆叠数量 |
| `+0x30` | 每件对象的数组 |
| `+0x38` | 件数组对象（压缩数组时交给它处理） |

每件对象 0x20 字节，`+0x1c` 是这一件是否占用的标记。工具、药物这类带耐久的东西，件对象里存着各自的状态。

### 取东西只有一个总闸

RVA 0x3E0310：

```c
void take_from_container(longlong dest, longlong src, longlong *item_def, int count);
```

- `src` 来源容器，`dest` 去向容器，`count < 0` 表示全拿，`*item_def` 等于全局量 `DAT_140834980` 表示「任意物品」。
- 逐件搬运：复制一件到目标容器里同种的条目，压掉来源里那一件，再 `DEC DWORD PTR [entry+0x28]`（RVA 0x3E04F8 与 0x3E072B 两处）。
- 某条目数量减到 0 就从容器里删掉（条目数 −1、数组前移）。
- 开始时广播事件 7，每搬一件广播事件 6（载荷带物品类别号），结束时刷新两个容器。

它自己是中性的：往里放、往外拿、交易、丢弃都调它。所以不能在这一层做「不扣」，否则交易和丢弃也会变成白给。

### 扣材料的那一步

真正决定「这次操作要扣多少」的是 RVA 0x342A60，签名：

```c
void collect_ingredients(longlong component, longlong *ctx, longlong *ingredient_list, longlong dest);
```

- `ctx[2]`（`+0x10`）是配方记录索引，配方记录 0x310 字节一条，表在 `[0x140926430]`；`ctx[3]`（`+0x18`）是材料的来源容器（仓库）。
- `ingredient_list` 里有材料条数（`+0x18`）、数组（`+0x20`，每条 0x18 字节）、批量除数（`+0x40`）；每条材料的 `+0xC` 是单件所需数量。
- 每种材料算一次数量，然后调 0x3E0310 把这些材料从仓库搬进目标容器：

```
数量 = ceil(单件所需 × 产出数量 / 批量除数) - 微小量取整
```

算完数量的最后一条指令在 **RVA 0x342BE0**（`F3 4C 0F 2C C9`，`CVTTSS2SI R9,XMM1`），结果放进第四个参数；紧接着 RVA 0x342BEC 才是调用（`E8 1F D7 09 00`，整个文件里只有这一处）。

这个函数有三个调用者，正好对应三类操作：

| 调用者 | 用途 |
| --- | --- |
| RVA 0x3435D0 | 开始制作（设状态 3、算时长、广播 `OnBeginCrafting`、事件 0xF5） |
| RVA 0x342E20 | 开始建造或升级：先扣材料，再找或新建 `KosovoConstructionComponent`，广播事件 0xB0，处理建造台与工匠 |
| RVA 0x3432B0 | 建造 / 升级的另一条开始路径（在栈上构造一个临时容器，材料先搬进去，再随事件 0xB0 交给建造组件） |

所以 RVA 0x342BEC 这一处就是「制作、建造、升级」共用的扣材料点。

### 为什么不能跳过搬材料

最直觉的改法是把这个调用整段换成空操作，但实测会崩游戏（访问违例，崩在 RVA 0x343381 的 `MOV RCX,[RAX]`）。

原因是这个调用不只是「搬东西」：它结束时还会刷新来源和去向两个容器（RVA 0x3DF850）。建造路径在栈上临时构造的空容器，正是靠这次刷新才成为可用状态。把整个调用跳掉，后面拿着这个没准备好的容器去广播事件 0xB0、交给建造组件，就会踩到未初始化的数据。

正确做法是**让搬运照常执行、只是搬 0 件**：把要搬的数量改成 0，函数该走的流程一步不少，容器该刷新的照常刷新，最后一件材料都不会少。数量为 0 时它内部的查找循环一次都不进，既不改堆叠数也不删条目，安全返回。

### 材料够不够的检查

在扣材料之前还有一道检查，决定「这次操作能不能开始」。

订单执行函数（RVA 0x344180）在派发之前会调一次虚表槽 `0x158`，返回值是假就什么都不做——这就是按钮变灰、点了没反应的原因。制作、建造、升级、自动建造四类组件在同一个槽位指向同一份实现 **RVA 0x342CF0**（已核对制作虚表 `0x140656158` 与建造虚表 `0x140656D78` 两处的槽值都是 `0x140342CF0`）。

它的逻辑很短：

```c
// RVA 0x342CF0 —— 材料够不够
broadcast_event(owner, 0xAA, 配方载荷, 1);            // 通知界面刷新材料高亮
for (每条材料) {
    条目 = 材料表->数组 + i * 0x18;
    if (查不到这条材料) continue;                     // 有的材料允许缺失
    拥有量 = count_item(仓库容器, 条目);               // RVA 0x3DF3C0
    需要量 = ceil(1.0 * 条目->单件所需);
    if (拥有量 < 需要量) return 0;                    // 材料不够，直接否掉
}
return 1;
```

所以「材料不扣」和「材料不够也能做」是两道不同的门：只改扣料点只能让已经够材料的操作不消耗，材料为 0 时仍然进不去。

### 工作台界面上还有三道闸

界面的按钮亮不亮，和上面那道检查是两套东西。它是分三步判出来的，任何一步没放开，表现都是「按钮是灰的、点不了」。

**一、打开工作台时直接禁用。** 面板打开函数（RVA 0x40D7B0，0x14040D7B0–0x14040DD32）每次打开都会把制作按钮关掉：先 `FUN_140089E40(BUTTON_CRAFT, "DISABLED", 1, 0)` 改显示状态，再 `FUN_140094CB0(BUTTON_CRAFT, 0, 1)` 真正置禁用位（RVA 0x40D9A6，字节 `E8 05 73 C8 FF`）。`FUN_140094CB0` 是控件的启用/禁用总开关，禁用位是控件 `+0x46` 的 bit3；教学按钮在教学开启时同样被关掉。

**二、列表构建时给每个配方算可做数。** RVA 0x40BB90 会把所有配方过一遍，替每个配方算出「还能做几个」，写进左侧列表项（面板 `+0x100` 处数组，每条 0x20 字节）：

| 列表项偏移 | 含义 |
| --- | --- |
| `+0xC` | 可做数 |
| `+0x18` | 可用字节 |
| `+0x10` | 需求信息指针 |

算出结果后，它按「可做数 != 0」得出可用的布尔，交给列表控件（RVA 0x3DE900 / 0x3DEB50）。

**三、每次选中配方都重新判一遍。** 列表选中回调是 RVA 0x40CEC0（由 0x40BB90 在 0x14040C430 注册）：

```c
// RVA 0x40CEC0 —— 选中配方
可用 = (列表项->可做数 > 0) && (列表项->可用字节 != 0);
FUN_140094CB0(BUTTON_CRAFT, 可用, 1);          // 按这次判定重新亮或灰
if (列表项->可用字节 == 0)
    FUN_140094CB0(按钮, 0, 1);                 // 第二道，再禁一次
```

判定用的两条指令是 RVA 0x40CF34 的 `76 0C`（`JBE`，可做数 ≤ 0 就跳到「不可用」）和 RVA 0x40CF3B 的 `74 05`（`JZ`，可用字节为 0 也跳），第二道的条件是 RVA 0x40CF86 的 `75 1A`（`JNZ`，可用字节非 0 就跳过禁用）。

**四、点击时还有两道。** 点下「制作」走到回调 RVA 0x40CC50，它自己又读了一遍同一份数据：RVA 0x40CCA0 的 `0F 86 63 01 00 00`（`JBE`，可做数 ≤ 0 就跳去拒绝）、RVA 0x40CCAB 的 `0F 84 58 01 00 00`（`JZ`，可用字节为 0 也跳去拒绝）。通过才广播事件 0x9A（制作请求），否则广播 0xA1（被拒绝），表现就是「点了没反应」。

### 扣完的材料去哪了

搬进目标容器只是暂存，之后还会被清掉：

- RVA 0x346C10（完成路径）：若配方记录 `+0xB8` 不等于 2，把工作台容器 `+0x128` 整批倒进全局容器 `0x140924F90`（任意物品 + 全拿），随后产出成品、广播事件 0xF5。
- RVA 0x343EC0（取消或重置）：状态清零、进度置 -1，把工作台容器 `+0x68` 里的东西倒回调用方给的容器，按情况广播事件 0x2E、0x74。
- RVA 0x343FB0（虚拟的「停止/结算」）：先按已完成比例把容器 `+0x68` 里的材料退一部分（RVA 0x3DFD50），再把外部容器整个拉进 `+0x68`。
- RVA 0x347920（组件事件处理）：事件 0xB0 时把上一个容器清空到载荷给的容器，新容器挂到 `+0x128`，配方 `+0xB8` 为 5/6 时广播 0xB1、0xB4。

### 其它动容器的路径

0x3E0310 还有一批调用者，都是「容器之间搬东西」而不是「从仓库扣材料」，例如完成时倒空、取消时返还、实体之间转交（RVA 0x348DA0）、产出分发（RVA 0x34A2E0 按随机目标分发）、放入物品时的借位（RVA 0x3E0C20）。这些不改也没关系，正好说明补丁点选在 0x342BEC 不会牵连交易和丢弃。

## 可选的功能实现方法

**本项目当前实现**：方案一，八处字节改写（下表三组），覆盖制作、建造、升级三类的开工与按钮状态。

### 方案一：八处字节改写（推荐，当前实现）

分三组，缺任何一组都会失败：

| 组 | 位置 | 原字节 | 改成 | 作用 |
| --- | --- | --- | --- | --- |
| 检查 | RVA `0x342CF0` | `40 57 48 83 EC 40` | `B8 01 00 00 00 C3` | 材料检查恒为「够」 |
| 搬运 | RVA `0x342BE0` | `F3 4C 0F 2C C9` | `45 31 C9 90 90` | 要搬的数量恒为 0，材料一件不少 |
| 界面 | RVA `0x40D9A6` | `E8 05 73 C8 FF` | `90 90 90 90 90` | 打开工作台时不禁用按钮 |
| 界面 | RVA `0x40CF34` | `76 0C` | `90 90` | 选中时「可做数 ≤ 0 → 不可用」不成立 |
| 界面 | RVA `0x40CF3B` | `74 05` | `90 90` | 选中时「可用字节为 0 → 不可用」不成立 |
| 界面 | RVA `0x40CF86` | `75 1A` | `EB 1A` | 选中时第二道禁用改为无条件跳过 |
| 界面 | RVA `0x40CCA0` | `0F 86 63 01 00 00` | `90 90 90 90 90 90` | 点击时不再因可做数为 0 拒绝 |
| 界面 | RVA `0x40CCAB` | `0F 84 58 01 00 00` | `90 90 90 90 90 90` | 点击时不再因可用字节为 0 拒绝 |

三组各管一件事：

- 检查那处是「允许开工」。它让检查函数开头直接返回 1，代价是跳过它内部的 0xAA 广播——实测没有副作用，界面刷新另有来源。
- 搬运那处是「不扣料」。注意改的是数量（`CVTTSS2SI` 换成 `XOR R9D,R9D`），不是把调用换成空操作：整个跳过会崩，原因见「为什么不能跳过搬材料」。
- 界面六处是「按钮能亮、点了有反应」。打开面板一处、选中配方三处、点击两处，缺一处就会卡在那一步。

改完之后：材料够时照常做、仓库不减；材料不够或为零也能做，产出照常给。三个入口（制作、建造、升级）共用检查与搬运那两处，改一次全覆盖；交易、丢弃、拾取走的还是它们自己的入口，不受影响。

开关顺序：先放开检查，再让搬运搬 0 件，最后打开界面三道闸（界面最后动，避免出现「按钮能点、实际进不去」的中间态）；关掉时按相反顺序恢复。

### 方案二：让「取出」永远不扣数（不推荐）

把 RVA 0x3E04F8 与 0x3E072B 的 `FF 4F 28`（`DEC DWORD PTR [RDI+0x28]`）改成 NOP。

任何取出都不减少来源数量，属于「全局白拿」：交易、丢弃都会变成「给了别人自己还有」。而且件数组仍会被压缩、数量却不减，同一格会出现「显示 N 个但只有很少几件」的不一致，带耐久的物品尤其容易出问题。

### 方案三：数据层每帧回填（不推荐）

每帧把仓库里关键物品的数量写回一个下限。游戏的「已占格数」是按 `容量 − Σceil(数量 / 格宽)` 现算的，凭空改数量会让已占格数突然变大，容易把容器撑爆或让界面显示错乱。

### 实现时要注意

- 定位用「模块基址 + RVA」；上面的字节只用来确认没认错位置（`0x342BEC` 那 5 字节、`0x342BE0` 那 5 字节在 v6.0.0 上都唯一；`0x40CF34`、`0x40CF3B`、`0x40CF86` 是 2 字节小指令，必须先读原始字节比对）。
- 改之前先读原始字节比对，只恢复自己写过的字节；如果这一处已经被别的修改器改过（`E8` 变成 `E9` 之类），先判断再决定动不动手。
- 八处要成组开关：只放开检查 = 按钮仍然灰；只打开界面 = 能点但进不去；只改搬运 = 材料照扣。同一组里的界面六处也要一起开，少一处就卡在那一步。
- 界面那几处判定**不要**改成「恒为可用」的常量：列表项被点亮、可做数却还是 0 时，详情面板会按 0 去算。要放开就放开比较与跳转本身（本实现就是这样做的），数据仍然是真实值。
- 关掉功能时要能原样恢复，否则仓库会持续「只进不出」。
