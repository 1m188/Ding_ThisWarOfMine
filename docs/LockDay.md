# 锁定白天时间 (LockDay)

## 功能语义

游戏里的时间分成"白天"和"夜晚"两段。白天从早上 6 点开始，到晚上 20 点结束；白天过完后进入夜晚。屏幕上右上角会显示当前时刻，刻度是 10 分钟。

"锁定白天时间"指的是：白天期间时钟不再往前走，右上角的时间停在当前这一格。它不动天数记录，也不会让白天提前结束。

需要点名的是：白天和夜晚共用同一块时钟结构（见下文"时钟状态"），所以实现时如果直接冻结那块结构，夜晚显示的时间也会跟着停。要做到只冻白天，就得在白天这一条路径上动手，本篇后面的方案就是按这个思路给的。

几个必须说清楚的边界：

- 锁定的是"时钟状态"，不是"游戏世界"。食物消耗、人物状态、AI 这些都还在按自己的节奏运行，只是它们看到的时间不再变化。
- 游戏本身有暂停功能（打开菜单时的暂停，以及控制台命令 `PauseGameClock`）。那是整套时钟一起停，白天和夜晚都停，和"只锁白天"不是一回事。
- 白天的进度被冻住之后，依赖进度推进才会发生的事（比如"到点了自动入夜"）也就不会自己发生。本篇只考证到时钟状态不再更新，入夜判定本身没有做实测。

## 游戏实现

### 时间参数

有一个静态参数对象，地址 RVA `0x923EE0`，里面放的是一组和时间有关的整数/浮点数。实测值：

| 偏移 | 值 | 含义 |
| --- | --- | --- |
| `+0x48` | 360.0f | 白天总长度（现实秒） |
| `+0x54` | 6 | 白天起始小时 |
| `+0x58` | 20 | 白天结束小时 |
| `+0x5C` | 5 | 夜间结束小时（夜里到 5 点） |
| `+0x6C` | 10 | 时钟粒度（分钟） |

白天 14 个游戏小时摊在 360 现实秒里，所以 1 个游戏小时约 25.7 现实秒，10 分钟刻度约 4.3 现实秒走一格。Lua 命令 `GetHourDurationInSeconds`（处理函数 RVA `0x236520`）返回的就是 25.7 这个数。

### 时钟状态

白天时钟的状态本身是一块静态结构，地址 RVA `0x8052B0`：

| 偏移 | 含义 |
| --- | --- |
| `+0x00` | 阶段种类 |
| `+0x04` | 当前小时（0–23） |
| `+0x08` | 当前分钟，按 10 分钟向下取整 |
| `+0x0C` | 映射模式：1 = 白天映射，0 = 夜间映射 |
| `+0x10` | 本阶段的进度，0–1 的浮点数 |
| `+0x14` | 本阶段总秒数（360） |

真正代表"白天走到哪儿了"的是 `+0x10` 这个进度值。屏幕上显示的小时和分钟都是从它换算出来的，游戏逻辑判断时间也是看它。

天数单独存放，地址 RVA `0x925110`。Lua 命令 `GetCurrentDay`（处理函数 RVA `0x236240`）读的就是它。

### 唯一的进度写入口

进度 `+0x10` 只被一个函数写过，RVA `0x3F5720`，可以叫它 `SetClockProgress`。它的工作分三步：

```c
void SetClockProgress(ClockState *s, float progress) {
    s->progress = progress;                 // +0x10
    if (s->mode == 0) {                     // +0x0C：夜间映射，换算式不同
        /* 21:00 → 05:00 那一套换算，见 docs/LockNight.md */
        return;
    }
    if (endHour < startHour)                 // 夜里跨过零点
        endHour += 24;
    float hours = (1.0f - progress) * startHour + endHour * progress;
    int minutes = (int)(hours * 60.0f);
    int hour = minutes / 60;
    minutes -= hour * 60;
    minutes = (minutes / 10) * 10;           // 按 10 分钟取整
    hour %= 24;
    s->minuteBlock = minutes;                // +0x08
    s->hour = hour;                          // +0x04
    if (minutes == 0 && hour == startHour)
        s->minuteBlock = 1;                  // 起始小时的特例分支
}
```

也就是说：外部只要把进度写进来，小时、分钟刻度会自动跟着变。

调用它的地方一共 9 处，分布在关卡时钟推进、阶段切换、界面刷新等不同路径上，而且每一处传进去的都是同一块结构（`0x8052B0`）。要注意这块结构是白天和夜晚共用的：`+0x0C` 决定用哪套换算式，白天开始时写成 1（RVA `0x2A46A0`），夜晚开始时写成 0（夜晚流程的进入函数 RVA `0x3F0D70`）。夜晚那一侧的换算式见 `docs/LockNight.md`。核对过的两条是：

- 界面刷新路径：先把日程表换算成进度（RVA `0x27FE20`，读的是 0x158 字节一条的日程记录表和天数），再调用 `SetClockProgress`。
- 关卡时钟路径（RVA `0x3FA210`）：读当前进度和白天起止小时，判断阶段状态后推进，再调回 `SetClockProgress`。

读进度 `0x8052C0` 的地方有 19 处，全部是读（`movss`/`mulss`/`subss`），没有一处直接写，因为写入一律走上面的函数。Lua 的 `GetCurrentHour`（RVA `0x236280`）就是这么读的。

### 阶段切换与暂停

- 阶段切换是另一个函数，RVA `0x3F5580`。它改阶段种类，并且**直接把进度清零**（`mov dword [rcx+0x10], 0`），然后重算小时和分钟。所以"锁时间"只影响白天内部的时间流动，不会阻止阶段切换函数本身把进度归零。
- 全局暂停标志在 RVA `0x92511D`，写它的函数是 `0x215860`。控制台命令 `PauseGameClock`（处理函数 RVA `0x2303F0`）就是把参数写进这个字节。这个标志一置位，整套时钟（包括夜晚）都停。

## 可选的功能实现方法

### 方案一：让"写入新进度"失效（推荐）

被改写的位置在 `SetClockProgress` 开头的第二条指令，RVA `0x3F5724`，一共 8 个字节：

```text
原始：0F 28 D9            movaps xmm3, xmm1
      F3 0F 11 59 10      movss  dword [rcx+0x10], xmm3

补丁：F3 0F 10 49 10      movss  xmm1, dword [rcx+0x10]
      0F 28 D9            movaps xmm3, xmm1
```

意思是：原来是把"传进来的新进度"存进结构体；改完之后变成"把结构体里的旧进度读出来"，后面照样把它放进 `xmm3` 继续算。于是函数每次都在用旧值重算小时和分钟，进度永远不变。

- 两种形式都是 8 字节（3+5 对 5+3），改写后不需要补 NOP，指令边界也不会错位。
- 这 8 字节在整份可执行文件里只出现一次，可以当唯一锚点用。
- 关闭时把原始 8 字节写回去即可。正确做法是先把当前内存读出来比对：如果已经是原始字节，说明本来就没开；如果是别的值（比如风灵月影也开着，它写的是它自己的形式），应当报冲突而不是直接覆盖。
- 只恢复自己写过的字节，这样别的修改器开的补丁不会被误伤。

### 方案二：直接往进度字段里写固定值

每帧把固定进度写回 `0x8052C0`。缺点是游戏自己每帧也在写同一个位置，两边抢，只能靠更高频率硬压，或者去抢在游戏之后执行；而且写值和换指令相比没有额外收益。不推荐。

### 方案三：拉长白天

改 `0x923F28`（也就是参数对象 `+0x48` 的白天总秒数）或者白天起止小时。这只能让白天变慢，不能让它停住，而且会连带改变 `GetHourDurationInSeconds` 给脚本的返回值。用途不同。

### 方案四：用游戏自带的暂停

把 `0x92511D` 写成 1，等价于控制台 `PauseGameClock true`。缺点是夜间、实体逻辑一起停，语义上不是"锁定白天时间"。

### 实现时要注意

- 补丁生效期间界面上的时间会停在当前 10 分钟刻度上，刻度不会自己跳。
- 阶段切换函数会直接把进度清零，所以"锁时间"最稳的用法是在白天内开启；如果要跨阶段保持，得另想办法。
- 这三个地址（`0x3F5724` 的字节、`0x8052B0` 的状态、`0x923EE0` 的参数）都建立在当前这份 2019 年 v6.0.0 可执行文件的布局上。

## FLiNG 实现

版本：This War of Mine v6.0.0 Plus 8 Trainer（2019-11-18），热键是小键盘 5。

实测方法：先读游戏 `.text` 全段（5,807,616 字节）做基线，后台注入一次小键盘 5 的按下抬起，再读一次做逐字节比对；连按两次、退出功能后再比对一次。两次未操作时的基线漂移是 0 字节，所以比对结果干净。

结果：整个 `.text` 只有 8 个字节变化，位置是 RVA `0x3F5724`，正好是上面方案一那 8 个字节：

```text
原始：0F 28 D9 F3 0F 11 59 10
补丁：F3 0F 10 49 10 0F 28 D9
```

再按一次小键盘 5，8 个字节精确还原成原始值。全过程没有出现新的可执行内存页，没有 trampoline，也没有标志位变量——是纯粹的就地改写，和它改"瞬间制作物品"的手法一致（那次改的是 RVA `0x345625` 的 2 个字节）。相比之下，它改"无限生命"时用的是跳转加远端代码页，因为那次要换掉一个**值**；这里只需要把"存新值"换成"读旧值"，改指令就够了。

它改完之后的效果是：`SetClockProgress` 收到的进度被丢弃，结构体里的进度、小时、分钟都不再更新，界面上白天的时间停住。夜晚因为共用这块结构，显示同样会停住；但夜晚自己的计时和推进不受这处补丁影响。

需要注意的两点：

- 风灵月影改写前后不校验原始字节，所以如果它和别的修改器同时改同一处，两边的"关闭"都会把对方的状态改坏。自己实现时应当先比对再改写，并且只恢复自己写进去的字节。
- 白天和夜晚是两个独立开关（小键盘 5 和 6）。这里考证的白天那个改的是上面这处，也就是"存新进度"这一步。白天和夜晚共用这块结构，所以这一处补丁在夜晚同样会让显示停住（存进去的进度一直是旧值）；但夜晚自己的推进（`docs/LockNight.md` 里那条夜间驱动链）是另一段代码，白天这处补丁管不到它。
